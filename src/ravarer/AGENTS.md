# Råvarer — arkitekturregler

- Oppskrift-PDF regner linjekost via `pdfLineCost` (verifisert status kreves) og viser ingen total/per stk når noe mangler. Why: manglende pris ble summert som 0 kr og ga full sum.
- Råvare-DataTable aktiverer desktop-rad, mobilkort og tastatur gjennom én `activate` (velg via `onActiveChange`, så åpne). Why: mobilkort ignorerte `onActiveChange`, så trykk i arbeidslistene gjorde ingenting.
- Kostgrunnlag per fakturalinje er tredelt (`lineEligibilityFrom`: gyldig/ukjent/ikke gyldig) fra de flettede historikkradene; serverens eligible uten bevist linjeidentitet (f.eks. låste snapshots, som projeksjonen utelater) er «ukjent», og projeksjonen er ukjent mens den hentes på nytt. Why: ID-snarvei ga «Gyldig» på feil linje, og streng identitet alene merket gyldige snapshots som ugyldige.
- Foreldreløse datablad slettes bare med én betinget DELETE (utvalg + selskap + `raw_material_id is null`) som returnerer faktisk slettede ID-er, etter eksplisitt bekreftelse. Why: les-så-slett kunne slette et blad som ble koblet i mellomtiden.
- Matvaretabellen-kobling går gjennom `useNutritionLinkFlow` (økt avsluttes ved lukk/avmontering; kontekst og tilgang kontrolleres rett før skriving; `force=true` bare for bekreftet par), og `parseApplyResult` krever full form + identitet — ellers ukjent utfall, aldri «koblet». Why: avbrutt dialog kunne fortsatt skrive, og tomt svar ble vist som koblet.
- Datablad-masseopplasting anvender bare en frosset, gjennomgått operasjon (`ReviewedOp`: selskap, generasjon, datablad, mål, felt, næringsfelt) etter før/etter-gjennomgang; synkron lås for anvend, kontekstsjekk før hver sideeffekt, og bare `applied:true` uten failures er anvendt (207 = delvis, uklart = ukjent). Why: alle felt ble sendt uten gjennomgang, dobbelttrykk/selskapsbytte ga foreldede skrivinger, og tomt svar ble «Anvendt».
- Varelistens avvik er «siste faktura mot gjeldende kostpris» og kommer bare fra `rm_list_price_evidence` via `useListPriceEvidence` (batcher à 100, høyst to samtidig, komplett og ferskt bevis bundet til radens `updated_at`/kostpris/enhet); null = ukjent, og samme `comparison` styrer tabell, mobilkort, filter, rekkefølge og CSV. Why: leverandørbufferens siste pris ga 3421,9 % for eske mot stk med uverifisert kost.
- Råvarekortets og peekens kostpris, sjekklistens prisgrunnlag (påkrevd `costEvidence`), siste fakturapris, avvik og pakningskost leser samme bundne `rm_list_price_evidence` via `useMaterialPriceEvidence` (`bindEvidence`/`costEvidenceFor`/`latestInvoiceOf`). Listens kostmerke/CSV og siste fakturadato bruker samme bevis. Lagret «verifisert» uten fersk bekreftelse vises aldri som verifisert, og leverandørbufferen brukes ikke. Why: KPI-ene viste en gammel bufret augustpris og 0 % selv om en nyere septemberfaktura var usikker.
- Leverandørkortet bruker `?seksjon=` (`supplierSections.ts`) og `?liste=` for retur; aliasendring går bare via `rm_supplier_alias_edit_preview`/`rm_edit_supplier_alias` (`useSupplierAliasEdit`, streng `parseAliasEditResult`, ukjent utfall krever ny lesing). Hele koblingsflytt forblir `rm_change_supplier_link`. Why: den gamle aliasvisningen var skrivebeskyttet og avkortet stille ved 50; direkte UPDATE ville omgått revisjon, token og revisjonslogg.
- Lagerhuben har seks `?fane=`-faner (`LAGER_TABS`); telling/bevegelser holdes montert etter første besøk, og panelene remonteres ved selskapsbytte. Why: nestede faner var ikke URL-styrt, og fanebytte mistet utkast/filtre.
- Varetelling sender bare en lagret, frosset innsending (`useCountSubmission` + `countSubmission.ts`: opId + ordnede linjer + notat) og låser skjemaet til utfallet er kjent; ukjent svar sendes uendret på nytt, og bare bevist avvisning + eksplisitt valg frigjør (ny opId kun ved 23505). Lokale utkast lagrer frosset `expected`; mangler den, kreves eksplisitt gjennomgang. Why: ny bygging fra redigerbare felt ga 23505/dobbeltrisiko, og lokal gjenopptakelse byttet stille konfliktgrunnlaget.
- Varemottak skiller bekreftet mottak (`rm_goods_receipts`) fra lagerbevegelse (purchase/return) via `receiptStatus.ts`; `rm_receive_invoice_line`-svar leses strengt (`parseReceiveResult`) og klienten skriver aldri bevegelse etter RPC-en. Why: bevegelse fra fakturatriggeren skjulte manglende mottak/parti, og kreditretur var usynlig.
- Leverandørens innkjøp (teller og nevner) hentes bare via `fetchSpendSummary` → `fetchAllCounted` (eksakt antall + keyset på id, antall sjekkes på nytt) og summeres i `summarizeSpend`; manglende mva/beløp gir `netNok=null`, andel bare via `spendShare`. Why: én spørring kunne avkortes av serverens radgrense og manglende mva ble 0.
- Avtalelagring og koblingsflytt leser svaret strengt (`parseApplyAgreementResult`, `parseChangeLinkStrict`) med synkron lås og frosset mål; transportfeil og feil uten SQL-kode er ukjent utfall. Ukjent utfall lagres utenfor dialogen (`agreementRecovery.ts`, `changeLinkPending.ts`), overlever lukk/åpne og frigjøres bare av avstemming mot lest kobling eller et eksplisitt valg — aldri automatisk nytt kall. Why: `{}`/nettverksfeil ble vist som lagret eller låst opp ved gjenåpning, og `rm_apply_agreement` legger til prishistorikk ved hvert kall.
- Fakturaflatens retur godtar bare `?…`-listekontekst eller trygge appstier for leverandør/lager (`fakturaReturn`); eksakt fakturavisning (`includeResolved`+`invoiceId`) henter alle linjer uansett fakturastatus, mens den globale køen utelater ferdige. Why: leverandørretur falt til Fakturaer og avstemte fakturaer viste «ingen linjer».
- Lager › Beholdning har `q`/`valgt`/`filter` i adressen for både videresalg og alle lagerførte (felles `DataTable`/`SplitView`/`StockPeek` med utvalgets egne fakta); fullt kort får `?lager=` via `stockFullHref` og råvarekortet går tilbake bare via validert `lagerReturnHref`. Nøkkeltall viser «…»/«–» ved lasting/feil, aldri 0. Why: retur fra kortet mistet lagerkonteksten og feilet henting ble vist som tomt lager.
- Mottaksavvik (manuell lagerbevegelse, ikke idempotent) bindes til frosset selskap+faktura+linje+vare, har synkron lås og gjeldende-kontekst-sjekk, og setter en markør i `adjustmentRecovery.ts` før kallet; uklart utfall (alt unntatt SQLSTATE-avslag) sperrer samme linje på tvers av lukk/åpne til eksplisitt «kontrollert bevegelsene», aldri automatisk nytt forsøk. Markøren lever bare i fanen. Why: lukking glemte uavklart bevegelse og inviterte til blind ny registrering.
- Forhandlingers lenkesvar leses bare via `parseRfqCredentials` (`negotiationOps.ts`) bundet til frosset mottakersett; valgt mottaker matches på ID, aldri første element, og tapt/feilet generering er ukjent (passord kan være rotert) uten automatisk nytt forsøk. Utfallsmotorens svar klassifiseres med `classifyApplyOutcome` (suksess/avvist/delvis/ukjent), og primærleverandør er et eget, gjentakbart steg. Råvarelista erstattes bare i et ekte utkast uten utstedte lenker (fersk lesing før `replace_child_rows`). Why: første-element-fallback kunne parre en leverandørs e-post med en annens passord, og erstatning slettet tilbud i kaskade.
- Leverandørportalene (`/tilbud/:token`, `/bekreftelse/:token`) kaller bare via `portal/portalApi.ts` (`callPortal`: ok/avvist/ukjent, strenge bunt-parsere bundet til egne linjer); ukjent innsending låser skjemaet til eksplisitt ny lesing, aldri automatisk nytt kall, og lenkebytte forkaster sene svar. Why: rå `any`-svar og nettverksfeil ble vist som «feilet» og inviterte til dobbel innsending.
- Forhandlingers flerstegs skrivinger fryser selskap+bruker+tilgang (modul OG fakturaspesifikk skriverett, lukket under lasting) ved start (`useWriteContext` i `useNegotiations.ts`) og kontrollerer før hver ny skriving; `replace_child_rows` krever kvittering = antall rader, ellers uklart utfall. Live-aktivering med ukjent utfall sperres til lest status + eksplisitt tillatelse, og feilet merking gjentar bare statussteget for frosne linjer; bekreftet aktivering fullfører statussteget også etter navigasjon, og gjenoppretting huskes per forhandling i fanens minne. Veiviseren eies per rute-ID + selskap (keyed remount). Tilbudsomregning bruker aldri råvarens globale pakningstall eller omregning mellom dimensjoner. Why: selskapsbytte midt i en lagring fortsatte i feil kontekst, og tom pris/global pakning ga oppdiktede vinnere og besparelser.
- Reberegning av kostpris (`useCostRecalc`) viser bare serverens dry-run som foreløpig forslag (`recalcContract.ts`, eksakt bulk-kontrakt) og skriver i bolker med kontekstsjekk før hver; bekreftede bolker/angring lagres i `recalcLedger.ts` som overlever ny skanning/nullstilling, ukjent utfall holdes til eksplisitt kontroll. Why: klientberegnet forslag ≠ skriverens verdi, og delvis feil/angring mistet kvitteringer.
- Gamle fakturalister oversetter `filter=` til `visning=` bare når moderne `visning` mangler (`legacyRoutes.ts`, `defaults`). Why: seedet `visning=alle` maskerte gammel «klar».
- Fakturalinjeretting fryser mål som selskap+faktura+linje i `FakturaWorkspace`; rute-/selskapsbytte lukker straks, og `CorrectLineDialog` krever at fersk rad har samme linje- og faktura-ID, et vellykket ferdig svar og uendret versjon (utkast beholdes ved ny henting), kontrollert synkront ved innsending. Why: et åpent mål kunne lagres mot gammel faktura mens ny faktura ble vist.
- `docs/ravarer-funksjonsmapping.json` bygges bare av `scripts/build-funksjonsmapping.mjs <base-sha>` fra original funksjonstekst i git, `docs/funksjonsmapping/review-owners.psv` og `prior-evidence.psv`, med fil-/import-/rute-/parserkontroll; kartlegging er aldri aksept. Why: seksjonsgjetting ga mappeplassholdere, ugyldige `fane`-verdier og nullstilte tidligere bevis.
- Reberegningens «Se serverens regnestykke» (R192) leser bare det eksisterende `recalc_raw_material_cost` med `p_dry_run: true` uten begrunnelse/overstyring, ved eksplisitt klikk per vare (`useSingleRecalcPreview`: én om gangen, frosset selskap+vare+generasjon, Råvarer-skriverett + fakturatilgang) og strengt via `parseSingleRecalcPreview`; visningen er dagens forslag, aldri erstatning for bulkforslag eller kvittering. Why: bulk-svaret har ingen linjeforklaring, og et nyere enkeltforslag er ikke det som ble kjørt.
- Modulens presentasjonsomfang settes som `data-active-app` på <html> via `ModuleScope` (`moduleScopeStore`: dybde-/token-eierskap, kun eget token fjernes); Råvarer-CSS overstyrer `--primary`/`--ring`/eyebrow der, app-fargen forblir dekor. Why: lys app-farge som tekst/knappefyll ga 1,8:1 kontrast, og portalerte dialoger må arve samme omfang.
- Nytt varetellingssystem (`src/ravarer/varetelling/`, tabeller `vt_*`) går bare via `VtApi` (`supabaseVtApi` i drift, `createFakeVtApi` i forhåndsvisning/tester) med strenge kvitteringsparsere; all skriving (også maler/steder) går via `vt_*`-RPC-er med op-id + revisjon, ventende operasjoner ligger i `pendingStore` per bruker+firma og sendes bare på nytt med samme op-id. Pris fryses bare via `_vt_price_evidence` (kanonisk `_rm_cost_candidates` + bundet kostpris; historisk kun eksplisitt), mengde beregnes av serveren fra frosne enheter, og låsrekkefølgen er telling → liste → linje. Sonden krever `vt_backend_version()`. SQL-en ligger i `supabase/pending/` til den er godkjent. Why: `verifisert` alene var foreldet bevis, klientsummer og parallelle statusendringer kunne endre godkjente tall, og tapte svar kunne gi dobbel skriving.
- «Alle priser» (panel + Pris-seksjon) er bare lesing via `AllPricesList` → `lib/allPrices.ts` på `useTimelineHistory`-rader: eldste først, Δ og median bare for `historyKind`=gyldig, avvik krever minst 3 priser og kjent grense (ukjent = ingen merker). Why: ikke-sammenlignbare rader skal aldri gi falske avvik eller prosent.
- Beslutninger (`/ravarer/beslutninger`, variant B) bygger bare på `rm_work_items` (sortering `oldest`) via `useDecisions`; spørsmålstype/tekst avledes i `lib/decisions.ts`, prisfakta i `lib/decisionFacts.ts`, og alle svar går gjennom eksisterende `VarekortPanel`/`FakturasakPanel`. Menytelleren bruker `openQuestionCount` på de samme tellerne. Beholdes bare for typene Fra faktura ikke dekker (kontroll, små prisendringer, videresalg/emballasje/råvare ikke klar). Why: én kø uten nye skriveveier eller tall som spriker mellom meny og side.
- Funksjoner fra ikke-kjørt PENDING-SQL kalles bare via `src/lib/pendingRpc.ts` (`callPendingRpc`/`pending*`, manglende funksjon/kolonne = «missing») og vises bare når `useCapability('rm_cap_<fase>_v1')` er true; ellers står det at flaten venter på databaseendringen. Why: koden skal virke som før til root har kjørt SQL-en, uten typer for objekter som ikke finnes.
- Svarknappene i Beslutninger (`QuickAnswers`/`useQuickAnswers`) gjenbruker PriceBlock-sperrene og dagens skriveveier (godta pris, «Ikke vare» = alltid, `rm_set_invoice_exclusion` = én gang, kravflyt, pakning via `rm_link_supplier_item`); siste svar for «Angre» ligger i fanens sessionStorage per selskap. Why: én beslutning skal ikke få egen skrivevei ved siden av varekortet.
- Prislinje-retting (bor under Varer › varens Pris-seksjon, `components/prislinje/RawMaterialPriceLines`; `rm_correct_purchase_price`, `rm_change_approved_package`) går forhåndsvisning→lagring med samme frosne opId; ukjent utfall låser skjemaet og tilbyr bare «send samme». Retting gjelder bare ett kjøp/framover og krever approve/admin. Regler/grense/automatikk bor i Innstillinger › «Automatikk og regler» (`pages/innstillinger/AutomatikkSettings.tsx`). Why: rettinger må være sporbare og aldri dobbeltført.
- Stillstandsvarselet for fakturalesing byttes til «Nøkkelen er testet og virker, venter på første lesing» bare via `readingBannerState` (lokal markør i `keyTestMarker.ts`, satt ved vellykket test av lagret nøkkel eller lagring av testet nøkkel) når testen er nyere enn siste feil. Why: nøkkeltesten etterlater ingen spor på serveren, og markøren er aldri bevis på at lesingen virker.
- «Fra faktura» (`/ravarer/fra-faktura`, `pages/frafaktura/`) er Råvarers hovedinngang for fakturaarbeid og erstatter Beslutninger i menyen (ruten og koden består, nås via «Øvrige spørsmål»). Nye varer leses sidevis (50) via `useNewItemsQueue` – `rm_new_items_queue` når `rm_cap_nye_varer_v1` finnes, ellers `rm_work_items` kobling→pakning med leverandørfilter på serveren – og skriver bare via `link-supplier-item`/`rm_link_supplier_item` med frosne linje-ID-er; prishopp godtas bare via `useQuickAnswers` (prissikkerhetsporten) og retting via `PackageFix`; ren logikk ligger i `lib/fraFaktura/`. Nye regler (grense, stille prisendring, pakning fra faktura, «Kalkylen bruker») er av til `20261119_fra_faktura` er kjørt. Why: forslag skal ikke bli varer før brukeren svarer, og ingen parallell skrivevei for kobling, pakning eller pris.
- Tunge arbeidsoppslag (`rm_work_items`, `rm_work_summary`, og menytellernes prislinje-/ikke-lest-henting med lav prioritet) går bare gjennom `workGate` (`lib/heavyGate.ts`, ett kall om gangen per fane, ett nytt forsøk ved tidsavbrudd); meny/faner leser tellere via `useWorkCounts`/`useNewItemsCount`, som gjenbruker ufiltrerte listesvar, og menyens oppsummering låner sidens fulle når den finnes. Why: 4–5 samtidige kall per sidevisning gikk alle ut på tid (8 s statement_timeout).
- «Fra faktura › Ikke lest» deler på lagrede linjer (`unreadGroup`): uten linjer går til lesekøen (`rm_requeue_invoice_line_extraction`), med linjer leses på nytt bare via dagens gjenlesing med forslag (`useBulkRereadRun`/`LesPaNytt`) eller godtas via `rm_accept_invoice_sum`/`rm_undo_accept_invoice_sum` (`useSumAccept`, op_id, streng `parseSumWrite`). Why: lesekøen hopper over fakturaer med linjer, så listen ble stående fast med en misvisende melding.
- Råvarer-menyen er Oversikt · Fra faktura · Varer · Fakturaer · Leverandører · Lager (+ Innstillinger); gamle `/ravarer/prislinje` og `/ravarer/automatikk` videresendes i `legacyRoutes.ts`. Kreditlinjer i Nye varer (`isCreditRow`) spør aldri om pakning og lenker til fakturaens kreditnotadialog. Why: Henriks beslutning 17.11.2026 – kun versjon D, ingen evne fjernes uten å være flyttet først.
- Samlet gjenlesing (Fra faktura › Ikke lest, `BulkRereadCard`) bruker bare dagens vei `rm_begin_invoice_reread` → `reread-invoice-preview` → `rm_apply_invoice_reread`; motoren (`hooks/samletGjenlesingRunner.ts`) lagrer fase per faktura i localStorage før hvert kall og gjenfinner påbegynt lesing i stedet for å starte ny, og omlasting krever «Fortsett». Automatisk bruk avgjøres bare av `lib/samletGjenlesing/rule.ts` (`decideAuto`: sum ok, manuell kobling gjenfunnet som samme vare, beskyttede linjer urørt; aldri dårligere sum). Why: én faktura skal aldri leses to ganger i samme kjøring, og ingen manuelle valg skal forsvinne uten gjennomgang.
